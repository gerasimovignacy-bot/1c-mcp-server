# План приёмки: снятие deny (PR #116, задача #114 пункт 2)

Для сессии живой приёмки. Код и живой прогон в одной сессии не делаются, поэтому
здесь всё, что нужно для прогона без контекста сессии разработки.

Ревизия сборки на момент написания плана: **`2026-08-05.1`**; актуальная на контурах —
**`2026-08-05.2`** (после #117 + #118). Ревизия НЕ зашита: проба берёт её из
`--revision <знач>` или `MCP_EXPECTED_REVISION`, по умолчанию `2026-08-05.3`. Ниже под
«ожидаемой ревизией» понимается это значение, а не конкретная строка.
Контуров три, политика стоит на всех:

| контур | endpoint | особенности |
|---|---|---|
| BUH_KORP | `https://laba-1c.astondevs.ru/BUH_KORP/hs/mcp/rpc` | БП КОРП 3.0.192.25 |
| ZUP_CORP | `https://laba-1c.astondevs.ru/ZUP_CORP/hs/mcp/rpc` | ЗУП КОРП 3.1.37.14, здесь ФИО |
| ERP_DEMO | `https://laba-1c.astondevs.ru/ERP_DEMO/hs/mcp/rpc` | ERP УП 2 2.5.27.70, **без авторизации** |

С `*_AUTH`-публикациями не работать: кредов нет, а блокировка учётки после
неудачных попыток кладёт **и** открытый `ERP_DEMO` — у них одна ИБ.

## Что изменилось и что, значит, проверяем

Контракт: **отказов нет ни в одной форме**. Раньше обращение к закрытому полю
отклонялось до выполнения; теперь запрос выполняется, строки возвращаются,
значение подменяется. Отсюда главное правило этой приёмки:

> Каждая проба двойная — «запрос принят» И «значение подменено». Одна половина
> ничего не доказывает: принятый запрос с открытым названием хуже отказа.

Три изменения по существу:

1. `deny` убран из контракта. Коды `privacy_denied_field`,
   `privacy_denied_autoorder`, `privacy_config_error` не возвращаются никогда;
   поле `mode` пропало из `get_current_user_context`. `mode` в JSON политики
   принимается и игнорируется, `deny` даёт предупреждение.
2. Нечитаемая секция политики → максимальная маска вместо отказа.
3. Числа и булево не закрываются; числовое поле в `type_field_masks` даёт
   предупреждение «маска не действует».

## Порядок прогона

### Шаг 0. Доказать деплой — до всего остального

```bash
node scripts/mcp_deploy_smoke.mjs
```

`engine_revision` обязан совпасть с ожидаемой ревизией на **каждом** контуре. Если хоть
где-то старая ревизия — дальше не идти: на старой сборке «запрос принят»
означает не снятие deny, а его отсутствие в политике, и вся матрица зелёная
ложно. Целевая проба (шаг 1) это проверяет сама и останавливается.

Деплой не атомарен. Старый `MCP_Tools` с новым `MCP_Security` падает на
`ЗапретPrivacyДляИнструмента` — если инструменты отвечают `internal_error`,
это неполная публикация комплекта, а не дефект правки.

### Шаг 1. Целевая проба этой правки

```bash
node scripts/privacy_drop_deny_probe.mjs --all --json reports/privacy_drop_deny_2026-08-05.json
```

По одному контуру: `MCP_URL=https://laba-1c.astondevs.ru/ZUP_CORP/hs/mcp/rpc node scripts/privacy_drop_deny_probe.mjs`

Разделы и смысл провала:

| раздел | что проверяет | FAIL означает |
|---|---|---|
| Р | ревизия, отсутствие `mode`, наличие аварийного режима | задеплоена не та сборка или контракт не обновлён |
| К | 13 форм, которые прежде получали отказ: принят + подменён | сборка отказывает там, где отказов нет, либо значение уходит открытым |
| И | `search_objects`, `get_object_by_ref`, `get_object_history` | инструмент блокирует вызов либо отдаёт имя открытым |
| Ч | числа и булево возвращаются как есть, предупреждение парсера | число закрыли — значение стёрто, а не подменено |
| П | парные пробы: открытый тип НЕ подменяется | ложная подмена, молча испорченная аналитика |

`N/A` отделён от `SKIP` намеренно: `SKIP` — «проверить не удалось», требует
разбора; `N/A` — «проверять нечем по существу». Не сваливать первое во второе.

### Шаг 2. Матрица §8 и приёмка политики

```bash
node scripts/privacy_gate_probe.mjs --json reports/privacy_gate_probe_2026-08-05.json
node scripts/privacy_acceptance.mjs --enforced --json reports/privacy_acceptance_2026-08-05.json
```

`privacy_gate_probe.mjs` в git не хранится (локальный инструмент). В нём §6
«обязан отказать» снята, её пробы переведены в §8.1 «обязан подменить»; §7
осталась и означает теперь «форма обязана выполниться».

### Шаг 3. Контракт целиком

```bash
node scripts/mcp_contract_test.mjs --all-response-modes --out reports/mcp_contract_report.1c-korp.latest.json
```

Из ответов исчез путь `privacy_config_error`, поэтому формат tool result задет —
прогон обязателен во всех трёх режимах.

**Базовые линии сверять по СОСТАВУ провалов, а не по числу тестов**: набор
растёт (88 → 122 → …), и числа из этого плана устаревают, не означая регресса.
Предсуществующие провалы, которые регрессом не считаются:

- BUH_KORP — `transport.unsupported_version_header_returns_400` (500 вместо 400);
  транспортные обрывы (категория `transport`) лечатся повтором;
- прежние 14 провалов ERP из-за `findAccountingRegister` (первый по алфавиту
  регистр без ресурса `Сумма`) и 5 провалов ZUP из-за захардкоженного
  `ПланСчетов.Хозрасчетный` в `query_examples` починены в фикстурах вместе с
  ревизией `2026-08-05.3` — их повторение на этой ревизии УЖЕ регресс оснастки.

## Что автоматика НЕ покрывает — нужна правка политики

Три вещи клиентом не вызываются: их включает администратор в
`MCP_ServerConfig`. Без этих проб приёмка **не полная** — так и записать, а не
считать зелёной.

### Числа

Проба Ч1 даёт `N/A`, если в `type_field_masks` нет числового или булева поля.
Добавить в политику любое числовое поле закрытого типа (например сумму или
количество) и ожидать:

1. `privacy.config_warnings` содержит «числовое или булево — маска на него не
   действует»;
2. запрос этого поля возвращает **число**, не `null` и не строку.

`null` в числовой колонке — это провал: значение стёрли вместо подмены, а решение
05.08.2026 требует обратного.

### `mode: deny`

В политике контуров deny-записей нет ни одной, поэтому ветка предупреждения
живьём не проверялась. Добавить `"mode": "deny"` в любую запись и ожидать:

1. запись **применена** как маска (тип продолжает закрываться);
2. в `config_warnings` — «значение mode "deny" больше не поддерживается — запись
   применена как маска, отказа не будет»;
3. `config_errors` пуст — политика в аварийный режим не уходит.

Проверить и неизвестное значение (`"mode": "wat"`): предупреждение другое
(«поле игнорируется»), запись всё равно применяется.

### Аварийный режим

**Способ включения ровно один — синтаксически битый JSON ВСЕЙ константы**
`MCP_ServerConfig` (например, удалённая закрывающая `}`). Прежняя рекомендация
этого плана — «строка вместо массива у секции» — **неверна и даёт ложно-зелёный
результат**: подмена типа секции аварию не включает, `МаскиПолейТиповLLM` делает
ранний возврат «не массив», и секция просто считается пустой (замер 05.08.2026,
ТЗ §4.8). Авария опознаётся по исключению из `ПрочитатьJSON`, а не по форме
секции.

До ревизии `2026-08-05.3` включать аварию бессмысленно: битый JSON ронял ВСЕ
методы JSON-RPC в `-32603`, включая `tools/list`, — падал единственный читатель
настройки без `Попытки` (`PrivacyPublishDetails`) на пути guidance каждого
tool-result. На `.3` и новее ожидаемое поведение — **данные возвращаются**:

1. инструменты работают, строки приходят, `isError` нет; `tools/list` и
   `get_current_user_context` отвечают, а не `-32603` (Ав2);
2. `privacy.config_errors` содержит «секция не прочитана … действует
   максимальная маска»;
3. `privacy.enabled` = `true`, а `guidance` начинается с объяснения аварийного
   режима — хотя применённых записей нет ни одной;
4. имя-подобные поля и представление закрыты у **любого** ссылочного типа,
   включая тип, которого в политике нет и никогда не было (Ав3) — проба
   «маскирование образца» информативна только если в образце есть ключ `type`
   с полным именем типа: структура без него проходит насквозь по построению;
5. **парная половина (Ав4, пропускать нельзя):** прочие поля (не имя-подобные)
   остаются открытыми. Сплошные `XXXXXXX` — провал: ответ, в котором закрыто
   всё, равнозначен отказу, от которого правка и уходит;
6. числа по-прежнему числа.

После пробы политику вернуть и убедиться, что `config_errors` снова пуст.

## Ловушки, на которых приёмка уже горела

- **Счёт как `kind: "string"`** в `В ИЕРАРХИИ(&Счет)` → **ноль строк без ошибки**.
  Только `{kind: "ref", type, uuid}`. Массив — только `{kind: "array", value: [...]}`.
- **`limit` у `list_metadata_objects`** — брать ≤ 100 и ходить страницами.
- **Поиск реквизита по синониму типа**: контур публикует синоним в
  ЕДИНСТВЕННОМ числе (`value_types: ["Контрагент"]`) — сверять вхождение в обе
  стороны, а не равенство полных имён.
- **`privacy` и `rows` лежат в КОРНЕ payload**, не под `data`.
- **Транспорт**: `node:https`, не `fetch` — undici рвёт connect на жёстких 10 с
  через VPN, и это выглядит как «упал контур». Обрыв лечится повтором; целевая
  проба повторяет сама.
- **Одновременное падение всех коннекторов** — это клиент, а не контур.
- **Пустое значение — не признак маски.** В целевой пробе пустое НЕ считается
  подменённым намеренно: иначе таблица без данных даёт зелёную матрицу.

## Гигиена результатов

- Живые данные контура в git, задачи, PR и комментарии **не попадают**: ни
  наименований, ни ФИО, ни адресов, ни uuid. Переносятся только выводы с
  обезличенными подстановками. Проверять до публикации, а не после.
- Отчёты прогонов в git не хранятся (`reports/` в `.gitignore`). В имени файла —
  дата и контур; слова `current` в имени не использовать.
- Целевая проба значения не печатает by design: вердикт строится на структурном
  признаке замаскированности. Не «улучшать» её выводом значений для отладки.

## Критерий готовности

Мержить PR #116 можно, когда на **всех трёх** контурах:

1. `engine_revision` равен ожидаемой ревизии (см. начало плана);
2. разделы Р, К, И, П целевой пробы — без FAIL;
3. раздел Ч — без FAIL, и хотя бы на одном контуре не `N/A` (то есть числовое
   поле в политику добавляли и предупреждение видели);
4. аварийный режим проверен намеренной порчей секции хотя бы на одном контуре, с
   обеими половинами: данные вернулись **и** лишнее не закрылось;
5. `mode: deny` проверен хотя бы на одном контуре;
6. контрактный прогон не хуже базовой линии своего контура.

Всё, что осталось `SKIP` или `N/A`, перечислить в отчёте поимённо. Зелёная
матрица говорит только о том, что проверено, а не о том, что закрыто: вердикт
«личные данные не уходят» по этой приёмке не выдаётся — он про раздел G #114.
